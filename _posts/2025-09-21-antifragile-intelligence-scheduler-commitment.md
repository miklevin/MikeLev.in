## Phase 1: The Seed - An Organic Approach

---

### Phase 1: The Seed - A Scheduler That Grows from Within

This initial phase establishes the core scheduling capability by integrating it directly into an existing, intuitive part of the UI: the **Tasks app**. This "flies under the radar" by avoiding a complex new interface and instead evolves a familiar one. The concept is simple: a task isn't just something *you* do; it's something the *system* can do.

* **Evolve the "Task" Concept:** The `060_tasks.py` app becomes the UI for managing scheduled jobs. We'll extend its database schema (`tasks` table) to include scheduling parameters: `schedule_type` (e.g., 'cron', 'interval', 'date'), `schedule_value` (e.g., `'*/5 * * * *'`, `'3600s'`), `last_run`, `next_run`, and `is_active`.
* **Integrate a Lightweight Scheduler:** We'll run a scheduler like `apscheduler.AsyncIOScheduler` in the background of `server.py`. On startup, it will read all "active" tasks from the database and add them to its schedule.
* **The "Task" Becomes an MCP Call:** The `text` field of a task will now be interpreted as a valid **MCP tool call string**. For example, a task with the text `[browser_scrape_page url=https://example.com]` will, when triggered, execute that exact tool call. This immediately leverages your entire existing tool ecosystem without needing to write new action handlers.
* **Minimal UI Change:** The UI in `060_tasks.py` will be subtly enhanced. When creating or editing a task, new optional fields (simple dropdowns and text inputs) will appear, allowing the user to set a schedule. A task without a schedule remains a simple to-do item.

This approach seeds the system with a powerful scheduler that feels like a natural extension of an existing feature, perfectly aligning with the "low profile" strategy.

## Phase 2: The Mycelial Network of Events

---

### Phase 2: The Mycelial Network - Antifragile, Event-Driven Triggers

This phase directly addresses your philosophy of heterogeneity and antifragility, moving beyond simple time-based triggers to create a resilient, interconnected system that resembles a mycelial network.

* **Introduce Trigger-Based Scheduling:** We'll add a new `schedule_type`: **'on_event'**. The `schedule_value` will be an "event name" that a job can listen for, such as `'workflow_finalized:hello_workflow'` or `'file_downloaded:my_data.csv'`.
* **Implement a System-Wide Event Bus:** A simple, in-memory event bus will be added to `server.py`. Any component in the system—a workflow step completing, an MCP tool running, a file being downloaded—can *publish* a named event to this bus.
* **The Scheduler Becomes a Subscriber:** The `apscheduler` instance will listen to this event bus. When it hears an event it's waiting for, it triggers the corresponding job(s). This creates a decentralized, reactive system.
* **Achieve Antifragility:** This design avoids the fragility of a rigid, linear pipeline. One workflow can fail and publish a `'workflow_failed:some_workflow'` event. A separate, independent "cleanup" or "notification" job can be listening for that specific failure event and run automatically. The system learns from and responds to stress, just like a mycelial network rerouting around damage. This directly counters the "cloned banana crop" problem.
